# アーキテクチャ

## 全体

```
ブラウザ(PWA)
   │  同一オリジン /api/** (セッションCookie)
   ▼
frontend: Nuxt 4 (Nitro)
   │
   ▼
backend: Go APIサーバ
   │  portインタフェース
   ▼
SQLite / CockroachDB
```

- frontendとbackendは独立して動作し、通信はOpenAPIで定義したHTTP APIのみ
- Nitroの`server/api/[...path].ts`は転送のみを担当、コアロジックを分離
- API定義は`api/`配下のTypeSpec(Goのサーバ型とTypeScriptの型はどちらも生成物であることに留意)

## バックエンドの層

```
cmd/mecalo           依存の構築(composition root)
internal/adapter/*   HTTP, DB, OIDC, 外部データ, パスワード
internal/app         ユースケース
internal/port        appが使うインタフェース
internal/domain/*    純粋ロジック
```

依存方向は`adapter → app → domain`, `app → port`。原則としてdomainは他レイヤに干渉しないこと。

| パッケージ | 責務 |
|---|---|
| `domain/nutrient` | 栄養素カタログ, 栄養値(量・状態・充足率), 合算 |
| `domain/food` | 食品, 不変のリビジョン, 単位換算, 検索キー |
| `domain/meal` | 記録(スナップショット), 日次集計 |
| `domain/recipe` | 材料と出来上がり重量からの算出 |
| `domain/target` | 食事摂取基準からの目標量算出と評価 |
| `adapter/httpapi` | 生成型と app 型の変換, 認証・CSRF・CORS |
| `adapter/sqlstore` | 両DB共通の SQL 実装。方言差分は `dialect.go` のみ |
| `adapter/dri` | 食事摂取基準 YAML の読込 |
| `adapter/foodsource/mext`, `adapter/foodsource/openfoodfacts` | 外部データの変換 |
| `adapter/foodsource/tabecal` | 外部検索(タベカル) |
| `adapter/foodsource/official` | 公式サイトの商品一覧の同期。取得元は`registry.go`へ登録し、商品ページの巡回は`detail.go`の共通処理を利用 |
| `adapter/foodsource/extract` | 栄養成分表示・HTML・PDFの表の解析の共通部品 |
| `adapter/foodsource/webfetch` | 外部サイト取得の共通処理(robots.txt, 間隔制御, 条件付きGET) |

## フロントエンドの構成

- `app/components/layout/`: レイアウトで利用するコンポーネント
- `app/components/shared/`: 複数画面で利用するコンポーネント(フォーム, グラフ, モーダル, 通知 等)
- `app/components/pages/<画面>/`: ページ固有コンポーネント
- 翻訳は`i18n/locales/<言語>/`にTSで置き、`common`(共通操作), `terms`(ドメイン用語), `layout`, `components`(共有部品), `pages/*`(画面と画面固有の部品), `errors`に分割。日本語を基準として他言語は`satisfies`で型検査
- 日付はday.js, ブラウザAPI系はVueUse, グラフはChart.js, 通知はvue-sonnerを利用すること(車輪の再発明は無駄でしかない上、維持コストが高いため極力避けるように！！！)
- アイコンはなるべくLucide系で統一したい

## デザイン方針

- 色は`app/assets/css/palette.css`のパレット変数を使い、色の直接指定は避けること
- ブランド3色(Soda Blue, Sakura Pink, Lavender)は淡い塗りとして使い、その上の文字は各色の濃色(`--soda-ink`, `--sakura-ink`, `--lavender-ink`)
- 画面全体の背景はブランド色の球体と粒子、カードは半透明の`.panel`を利用すること
- 書体は見出しと数字がUnbounded, 英字の小見出しがIBM Plex Mono, 本文がZen Kaku Gothic Newで統一
- 操作には押下時の縮小, ホバー時に右から差し込む背景など、インタラクティブな要素には視覚的な反応を付与する
- 3D要素は原則トゥーン調とする(3段階の陰影と輪郭線, `utils/three/toon.ts`)

## アクセシビリティ

可能な限りWCAG 2.2 AA相当を目標とする

- 文字は背景とのコントラスト比4.5以上、操作部品の枠・フォーカス表示・意味を持つ図形は3以上
  - 操作部品の枠は`--input-border`, フォーカス表示は`--focus-ring`を利用
  - フォーカス表示は枠線と淡いにじみで示す(強制カラーモード用に透明のoutlineを残すこと)
- 色だけで区別する前提のUIを設計しない
  - 判定ラベルはアイコンと文字を併記
  - リンクを色だけで区別するのは単独配置の場合のみに限定し、文中等は下線付きに
- 極力セマンティックに、なるべく標準要素を優先(dialog, meter, fieldset/radio, details/summary, time, table等)。HeadlessUIとReka UIは標準要素で表せないコンポーネント(タブ, リストボックス, カレンダー)でのみ利用
- フォームは`FormField`でラベル・説明・エラーをidで関連付け、エラー時は`aria-invalid`と`role="alert"`
- グラフと3D表示は読み上げ対象外とし、同じ値を必ずなんらかの手段で示す
- アイコンのみのボタンには`aria-label`を付与、44px以上の正方形とする
- 固定ナビの裏にフォーカスが隠れないよう、スクロール位置には余白を前提としたデザインとする
- 視差効果を減らす設定ではアニメーションを停止できるように
- 変更時はaxe-coreで主要画面に違反がないことを確認

## 栄養値の扱い

- 栄養値は`量 + 状態 + 充足率`の組み合わせ。状態はmeasured / estimated / trace / missing / calculated
- 成分表の`-`はmissing(未計測), `Tr`はtrace(集計上0), 括弧付きの値はestimated
- 合算は既知の値のみを加算し、栄養素ごとに値が判明している重量の割合を充足率として持つ
- 不足判定は充足率が0.8未満であれば判定不能とする。過剰判定は判明分のみ

## 記録の不変性

記録した食事の栄養値は、食品データの更新後も変わらないように

1. 食品リビジョンは作成後に変更しない。編集・公式データの再取込は新リビジョンの追加, 削除は論理削除で行うこと
2. 記録時に栄養値をスナップショットとして`meal_entry_nutrients`へ保存。集計はこのスナップショットのみ、食品テーブルを参照しない


## 外部取得元

取得元は`port/sources.go`の3種類に分離しておき、`MECALO_SOURCES`で有効化する

| 種類 | port | 実行契機 | 保存 |
|---|---|---|---|
| バーコード照会 | `ProductLookup` | 未登録バーコードの読取時 | 照会した商品のみ |
| 外部検索 | `FoodFinder` | 利用者の「外部のデータも検索」操作時のみに限定 | 応答は`source_cache`に1日, 選択商品のみ食品として保存 |

- タベカルは取得元側の部分一致に加え、チェーン一覧(1日1回取得)と検索語をbigram照合、近似するチェーンがあればチェーン内を検索を行う
| 一覧の同期 | `Catalog` | `mecalo sync`, `serve`内の定期実行(`MECALO_SYNC_INTERVAL`) | 全商品を食品として保存 |

- 食品IDは`<取得元>-<取得元の識別子>`, JANは`food.NormalizeBarcode`で正規化
- 取得元の識別子が同じ既存食品(旧形式IDを含む)は同一食品として新リビジョンを追加
- 地域で値が異なる取得元は全地域分を取得し、全地域で同じ値は1件, 異なる値は値ごとに商品名へ地域を併記(例: `紅しゃけ(北海道・東北)`)
- 一覧に2回続けて現れない食品は販売終了(`discontinued_at`)として検索から除外すること。記録はスナップショットのため影響なし
- 外部サイトの取得は1回120秒まで, 接続失敗・タイムアウト・5xx・429は間隔を空けて3回まで試行。それでも取得できない商品は読み飛ばし、登録済みなら販売終了の判定から除外して前回の内容を維持
- 詳細ページの再取得は30日ごと, それ以外は一覧での存在確認のみ(`source_items.fetched_at`)
- 一覧ページは条件付きGETで変更を判定, 全ページ変更なしの場合は取込と販売終了判定を省略
- 検索結果はJAN、ブランドと名前が同じ食品を1件にまとめ、 利用者の登録 > 公式サイト > タベカル > 成分表 > Open Food Factsの優先順で代表を選択

## 栄養値の基準量

- 栄養値は既定で可食部100gあたり。`Revision.Basis`指定時はその1単位(1個, 1食等)あたり
- 外食等で1単位の重量が公表されていない場合は重量0で保存し、記録はその単位でのみ可能
- 重量不明の記録は充足率の重み付けに、たんぱく質・脂質・炭水化物・食塩相当量の合計重量を利用する

## 食品検索

- 食品名はNFKC正規化, カタカナのひらがな化, 小文字化した検索キーで部分一致検索。語の区切りは空白1つとして保持します
- 空白区切りの各語をすべて含む食品が対象
- 食品名と別名は表記の検索キーに加え、形態素解析で得た読みの検索キーも保存。検索語も読みへ変換して照合します(e.x. 「人参」→「にんじん」)
- 成分表の取込時に備考欄の別名を食品の別名として保持する(例: オートミール→オート, オーツ)。自分で登録する食品にも別名を設定可能に
- 該当がない場合は、検索語を漢字1文字ずつの読みと2文字以上のかなに分け、すべてを含む食品を検索(例: 「豚ロース」→「ぶた」「ろーす」, 「ご飯」→「めし」)
- 検索結果から選んだ食品を検索語と対応付けて利用者ごとに保存、次回は文字列が一致せずとも上位に表示
- 並び順は、検索語との対応付け, 記録回数, お気に入り, 語単位の一致(末尾一致優先)の順に重視
- 検索キーの生成規則を変えた場合は`searchIndexVersion`の変更に応じて起動時に全食品の検索キーを再計算する(漏れがないように！！)

## オフライン

- Service Workerがアプリの画面とAPIのGET応答を保持し、通信できない場合は保存済みの応答を表示(=GETリクエストに副作用のあるエンドポイントを作らないこと)
- 食事の追加・変更・削除と体重の記録は、送信できない場合localStorageの送信待ちに保存、再接続・画面復帰・30秒ごとに先頭から順に送信
- 食事の追加は端末で生成した`clientRef`を付けて送るため、再送しても重複なし。変更・体重は上書き, 削除は削除済みでも成功として扱う
- 4xxで送信できなかった操作は画面上部に表示し、破棄か再試行かを利用者が選択する形をとる
- 未同期の記録はホーム画面に未同期表示、集計には含めない

## 目標量

`backend/data/dri/2025.yaml`に転記した食事摂取基準から算出

- 推定エネルギー必要量 = 基礎代謝基準値 × 体重 × 身体活動レベル + 目的に応じた調整量
- たんぱく質・脂質・炭水化物の目標量(%エネルギー)はエネルギー目標からグラムへ換算
- プロフィールは適用開始日付きで履歴を持ち、過去日の評価には当時の設定を利用

## 認証

- local: ログイン名とパスワード(argon2id)
- oidc: Authorization Code + PKCE(S256)
- セッションはHttpOnly・SameSite=LaxのCookie。状態変更リクエストには`X-Mecalo-Request`ヘッダ必須

## 外部サービス

外部への通信は次の場合のみ発生し、いずれも既定で無効あるいは管理者の明示操作に限る

- `mecalo import mext`: 成分表Excelの取得
- `MECALO_OPENFOODFACTS_LOOKUP=true`: 未登録バーコードの照会
- `MECALO_SOURCES`: 外部検索, 一覧の同期(上記「外部取得元」)
- `MECALO_AUTH_PROVIDERS`に`oidc`を含める場合: OIDCプロバイダとの通信

LLM連携等を追加する場合も`port`にインタフェースを定義、設定でオプトインする形にしたい
